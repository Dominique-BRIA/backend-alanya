# Courrier sortant : passer de Gmail à Postmark

**11 septembre 2026** · codes de vérification (inscription, mot de passe oublié,
changement d'adresse, double authentification)

---

## Pourquoi

| Gmail (aujourd'hui) | Postmark |
|---|---|
| 500 destinataires par jour, puis envoi **suspendu 24 h** | Pas de plafond journalier |
| Expéditeur `@gmail.com` : aucune signature possible, les codes tombent en indésirables | Expéditeur `@alanyavox.com`, signé DKIM |
| Le mot de passe d'application ouvre **toute la messagerie** du compte | Le jeton ne sait qu'envoyer |

---

## Ce que fait le code

- `src/lib/courriel.mjs` choisit le fournisseur et parle à l'API Postmark.
- `src/lib/mailer.ts` l'utilise ; le reste du backend n'a pas changé.
- `MAIL_PROVIDER` décide :

| Valeur | Effet |
|---|---|
| `postmark` | Postmark seul. Sans jeton : aucun envoi, erreur claire. |
| `smtp` | L'ancien relais Gmail seul. **C'est le retour arrière.** |
| `auto` ou absent | Postmark si `POSTMARK_SERVER_TOKEN` est rempli, sinon SMTP. |

- **Déployer le code ne change rien** tant que le jeton n'est pas posé : les codes
  continuent de partir par Gmail.
- Un échec Postmark **ne retombe pas** sur Gmail : il est journalisé et remonté
  (502 côté client), comme un échec SMTP aujourd'hui.
- Contrôles hors ligne : `node src/lib/courriel.mjs` (26 cas).

## Mise en service, dans l'ordre

### 1. Postmark

1. Créer le compte sur postmarkapp.com.
2. Créer un serveur, par exemple **Alanya production**.
3. **Sender Signatures → Domains → Add Domain** : `alanyavox.com`.
4. Demander l'**approbation du compte** tout de suite (bouton « Request approval »).
   Décrire l'usage : codes de vérification transactionnels, pas de marketing.

⚠️ Tant que le compte n'est pas approuvé, Postmark n'envoie **qu'aux adresses
`@alanyavox.com`** (refus `ErrorCode 412` pour les autres).

### 2. DNS chez OVH (zone `alanyavox.com`)

Postmark affiche les valeurs exactes à l'étape 1.3. Trois enregistrements :

| Type | Sous-domaine | Valeur | Rôle |
|---|---|---|---|
| TXT | `<sélecteur>pm._domainkey` | `k=rsa;p=…` (fourni par Postmark) | Signature DKIM |
| CNAME | `pm-bounces` | `pm.mtasv.net.` | Adresse de retour : aligne SPF et reçoit les rebonds |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:<adresse>` | DMARC, **absent aujourd'hui** |

- **Ne pas toucher au SPF actuel** (`v=spf1 include:mx.ovh.com -all`) : Postmark
  n'en a pas besoin, l'adresse de retour `pm-bounces` s'en charge.
- DMARC : commencer en `p=none` (on observe), passer à `p=quarantine` après
  quelques semaines sans anomalie.
- Revenir dans Postmark et cliquer **Verify** jusqu'à ce que DKIM et Return-Path
  soient au vert.

### 3. Déployer le code

Comme d'habitude (`deployer.sh` ou la commande de la mémoire de déploiement).
Aucune migration, aucune dépendance nouvelle.

### 4. `.env` du VPS (`~/backend-alanya/.env`)

Ajouter, **sans guillemets** :

```env
MAIL_PROVIDER=postmark
POSTMARK_SERVER_TOKEN=<jeton : Servers > Alanya production > API Tokens>
POSTMARK_FROM=Alanya <no-reply@alanyavox.com>
POSTMARK_MESSAGE_STREAM=outbound
```

- **Garder** `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` pendant une ou deux
  semaines : ce sont eux qui servent au retour arrière.
- Puis recharger l'API, **sans reconstruire** :

```bash
pm2 restart alanya-api --update-env
```

### 5. Vérifier

1. Depuis l'app, « Mot de passe oublié » sur **ton propre compte**.
2. Journal : `pm2 logs alanya-api --lines 50 | grep mailer`
   doit afficher `code envoyé par Postmark à …`.
3. Postmark → **Activity** : le message y apparaît, avec son statut de remise.
4. Le courriel reçu : expéditeur `no-reply@alanyavox.com`, pas dans les
   indésirables.

## Retour arrière

```bash
# dans ~/backend-alanya/.env
MAIL_PROVIDER=smtp
```

```bash
pm2 restart alanya-api --update-env
```

Effet immédiat, sans redéploiement.

## Après deux semaines sans incident

1. Retirer `SMTP_PASS` du `.env` du VPS.
2. **Révoquer le mot de passe d'application** dans le compte Google
   (Sécurité → Mots de passe des applications).
3. Plus tard, retirer `nodemailer` du code.

## Messages d'erreur à connaître

Ils apparaissent dans `pm2 logs` et dans `verification.livraison_detail`.

| Message | Cause | Que faire |
|---|---|---|
| `Postmark 401 (code 10)` | Jeton faux ou révoqué | Recopier le jeton du **serveur**, pas celui du compte |
| `Postmark 422 (code 400)` | Expéditeur non vérifié | Finir l'étape DNS, ou corriger `POSTMARK_FROM` |
| `Postmark 422 (code 406)` | Destinataire désactivé après un rebond ou une plainte | Postmark → Suppressions → réactiver l'adresse |
| `Postmark 422 (code 412)` | Compte pas encore approuvé | Attendre l'approbation (étape 1.4) |
| `Postmark injoignable` | Réseau du VPS, ou délai de 10 s dépassé | Vérifier la sortie réseau du VPS |

En cas de succès, `livraison_detail` vaut `postmark <MessageID>` : c'est
l'identifiant à chercher dans Postmark → Activity.
